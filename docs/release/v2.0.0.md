# pack-io v2.0.0 — Hardening and Safe Schema Evolution

**Released:** 2026-10-13
**Status:** stable major release. It adds security hardening,
silent-corruption fixes, safe field retirement and `Box<T>`. The wire
format is unchanged.

---

## Summary

The October 2026 library audit found that the crate's headline promise
did not hold. That promise was "no panic, no unbounded allocation, on
any byte sequence". The audit found:

- five bytes could make the decoder allocate 1 GiB;
- a versioned struct threw away the caller's allocation cap;
- about 5 KB of nested input crashed the process with a stack overflow;
- removing a field could make older readers decode the next field's
  bytes into it, without any error;
- the zero-copy derive mis-parsed versioned structs;
- the `serde` feature compiled no code.

v2.0.0 fixes all of it:

- Decoding is bounded by the input, by a per-value cap, and by a
  nesting limit.
- Versioned bodies are decoded under the caller's limits.
- The view derive reads versioned frames.
- Fields can be retired without corrupting older readers.
- Misused derive attributes are compile errors.

It also adds an opt-in canonical decode mode, a real serde adapter,
`bytes` integration, `Box<T>`, new derive attributes and more
standard-library impls.

**The bytes do not change.** Every byte string a 1.x encoder produced
for valid data is produced identically and decodes to the same value.
This is checked against golden vectors written by 1.0.1. It is a major
version because of three kinds of change, each listed below with its
migration:

- decoders now reject some hostile or invalid input that 1.x accepted;
- the derive rejects attributes that 1.x silently ignored;
- `Box<T>`'s new blanket impl can conflict with impls downstream crates
  wrote.

Before publication an independent re-audit found four contract gaps in
the first 2.0.0 tree and a set of smaller items. All are fixed in this
release; see [Re-audit fixes](#re-audit-fixes-before-publication).

## Highlights

- **Bounded allocation.** A hostile length prefix costs nothing in
  memory on the in-memory decoder, or one 64 KiB chunk on the streaming
  decoder, down from up to 1 GiB.
- **Depth limit.** `Config::max_depth` (default 128) turns stack-overflow
  aborts on hostile nested input into `SerialError::DepthLimitExceeded`.
- **`#[pack_io(retired = N)]`** takes a field out of use while keeping
  its slot. Readers built before the change stay aligned and see the
  default. `removed = N` keeps the 1.x `deprecated` encoding.
- **`Box<T>`** for every `T`, so recursive types derive directly.
- **Versioned structs** decode under the caller's `Config`, borrow their
  body instead of copying it, and reject version 0. `DeserializeView`
  reads their frames, where 1.x mis-parsed them.
- **Canonical decoding.** `Config::with_canonical(true)` accepts only
  the encoder's own bytes, for hashing and signing; a versioned struct
  only at the reader's own version. It stays opt-in; see
  [Canonical decoding](#canonical-decoding-stays-opt-in).
- **`pack_io::serde`** puts serde types on the pack-io wire,
  byte-identical to the native derive (set fields through
  `pack_io::serde::sorted_set`, because serde has no set type).
- **New derive attributes** `skip`, `default`, `with`, `crate`, `index`.
- **New impls**: `char`, `NonZero*`, `Duration`, `VecDeque`, `Box`,
  `Rc`, `Arc`, `Cow`, `PhantomData`, `bytes::Bytes` / `BytesMut`.
- **Faster** versioned-struct encode and decode, map encode,
  `[u8; N]` encode and decode, and `Vec<u8>` and `Vec<u64>` decode.
  Numbers and the one remaining regression are [below](#performance).

## Breaking changes

| # | Change | Who is affected | Fix |
|---|---|---|---|
| 1 | Nesting deeper than `max_depth` (128) fails with `DepthLimitExceeded` | decoders of trusted data nested > 128 derived levels | `Config::with_max_depth` |
| 2 | Version `0` in a versioned payload fails with `InvalidVersion` | only hand-made or corrupt payloads (no encoder writes 0) | none needed |
| 3 | `decode_from` stops at `max_alloc` (1 GiB) | streams decoded in one value larger than 1 GiB | `decode_from_with_config` |
| 4 | Unknown, duplicated or misplaced `#[pack_io]` attributes, and `since > version`, are compile errors | code with attributes 1.x ignored (or that silently dropped a field) | delete or correct the attribute |
| 5 | `skip` / `default` / `with` / `index` on enum variants and enum fields are honoured | enums carrying such attributes; **their encoding changes** | remove the attribute to keep 1.x bytes |
| 6 | `#[pack_io(deprecated = N)]` is a compile error | every versioned struct that deprecated a field | `removed = N` (same bytes), or `retired = N` for new retirements |
| 7 | `Box<T>` has blanket `Serialize` / `Deserialize` / `DeserializeView` impls | crates that implemented pack-io traits for `Box<TheirType>` | delete those impls (same bytes) |
| 8 | `max_alloc == 0` reports `InvalidConfig` (was `InvalidLength { declared: 0, .. }`) | code matching that error | match `InvalidConfig` |
| 9 | A Rust discriminant that differs from the variant's wire tag, and `removed = N` more than one version ahead of `version`, are compile errors | enums with `A = 5`-style discriminants (1.x ignored them); typo'd `deprecated` versions | `#[pack_io(index = N)]`; correct `N` |
| 10 | Collection elements that occupy no input bytes (`Box<()>`, all-`skip` structs, zero-sized types) are limited to `max_alloc` bytes per decode | messages with more than `max_alloc` bytes' worth of such elements | raise `max_alloc` |

`cargo semver-checks` against 1.0.1 agrees that 2.0.0 is consistent. Its
196 API-signature lints all pass even for a minor bump, because none of
them covers behaviour changes, derive-macro output, or a new blanket impl
on a `#[fundamental]` type. Every change in the table falls into one of
those three gaps. The major version is therefore decided by
`VERSIONING.md` §4, not by the tool.

## Upgrading from 1.x

Bump `pack-io = "2"` and build. The full guide with every snippet,
doc-tested on each build, is
[`docs/MIGRATION.md`](https://github.com/jamesgober/pack-io/blob/main/docs/MIGRATION.md).
In short:

**1. Deeply nested trusted data.**

```rust
// 1.x: let tree: Tree = pack_io::decode(&bytes)?;
let tree: Tree = pack_io::decode_with_config(&bytes, Config::new().with_max_depth(1024))?;
```

**2. Version 0.** No code change. If you match on the error:

```rust
Err(SerialError::InvalidVersion { version: 0 }) => { /* corrupt or hand-made payload */ }
```

**3. Streams larger than 1 GiB through `decode_from`.**

```rust
// 1.x: let snap: Snapshot = pack_io::decode_from(&mut file)?;
let snap: Snapshot = pack_io::decode_from_with_config(&mut file, Config::new().with_max_alloc(4 << 30))?;
```

**4. Derive attribute errors.** The error points at an attribute that
never worked. For a too-new `since`, give the struct that version:

```rust
// 1.x compiled this and never encoded `email`:
// #[pack_io(version = 2)] struct User { id: u64, #[pack_io(since = 3)] email: String }
#[pack_io(version = 3)]
struct User { id: u64, #[pack_io(since = 3)] email: String }
```

**5. Attributes on enums.** Search for `#[pack_io(` inside enums before
upgrading. To keep the 1.x bytes, remove the attribute 1.x ignored:

```rust
// 1.x encoded `cache` despite the attribute:
// enum Msg { Data { id: u32, #[pack_io(skip)] cache: Vec<u8> } }
enum Msg { Data { id: u32, cache: Vec<u8> } }
```

**6. `deprecated = N`.** For fields already deprecated in deployed
data, keep the bytes:

```rust
// 1.x: #[pack_io(deprecated = 3)] legacy_token: String,
#[pack_io(removed = 3)] legacy_token: String,
```

For a new retirement at a new version, prefer the slot-keeping form:

```rust
#[pack_io(retired = 4)] legacy_token: String,
```

Do not change an existing `deprecated = N` into `retired = N` at the
same `N`, because version-`N` payloads written by 1.x have no slot.

**7. `Box` impls.** Delete them; recursive types derive directly:

```rust
// 1.x: impl pack_io::Serialize for Box<Node> { ... }  (delete)
#[derive(Serialize, Deserialize)]
struct Node { value: u8, next: Option<Box<Node>> }
```

**8. Zero `max_alloc`.**

```rust
// 1.x: Err(SerialError::InvalidLength { declared: 0, .. })
Err(SerialError::InvalidConfig { .. })
```

**9. Discriminants.** Keep the tag the variant always had:

```rust
// 1.x encoded `Warn = 7` as tag 1.
enum Level { Info = 0, #[pack_io(index = 1)] Warn = 7 }
```

**10. Elements with no input bytes.** Only messages carrying more than
`max_alloc` bytes' worth of `Box<()>`-like elements are affected; raise
`max_alloc` for those.

## What changed

### Security

| Finding | Before (1.0.1) | After (2.0.0) |
|---|---|---|
| PACK-001: `decode::<Vec<u8>>` of `varint(2^30)` (5 bytes) | allocates and zeroes 1 GiB, then fails | fails with `UnexpectedEof`; 0 bytes allocated |
| PACK-002: `IoDecoder::read::<String>()` of the same 5 bytes | allocates 1 GiB before reading | allocates one 64 KiB chunk; buffers grow only as data arrives |
| PACK-003: versioned body declaring 1 GiB | 1 GiB allocated | rejected before reading (body length > remaining input) |
| PACK-003: versioned body with an inner 1 MiB `Vec<u8>` under `max_alloc = 64` | 1 MiB allocated (cap ignored) | `InvalidLength`; 0 bytes allocated |
| PACK-004: 5,000 levels of `Node { children: Vec<Node> }` | process aborts (stack overflow) | `DepthLimitExceeded` at level 129 |
| PACK-011: `decode_from` on an endless reader | reads until out of memory | stops at `max_alloc` (+1 byte) with `InvalidLength` |
| PACK-R01: `Vec<Box<()>>` of `varint(2^27)` (4 bytes) | 1 GiB allocated; larger counts abort on out-of-memory | elements that consume no input are charged against `max_alloc` for the whole decode: under a 1 MiB cap, peak memory stays under 2 MiB |
| PACK-R10: 127 nested hostile counts on a stalled `IoDecoder` | about 10 MB pinned | 4 KiB per open level |

The regression tests are:

- `tests/alloc_bounds.rs`, which measures every case with a counting
  allocator;
- `tests/depth_limit.rs`, which covers recursion, including a check
  that the default limit fits a 1 MiB stack in a debug build;
- `tests/std_types.rs`, which applies the same limit to recursion
  through `Box`.

The fuzz harness now runs with `-malloc_limit_mb=64`. That reports the
1.0.1 behaviour as an out-of-memory crash, and 2.0.0 passes.

### Schema evolution (PACK-005)

In 1.x, `#[pack_io(deprecated = N)]` removed a field's bytes from the
middle of the body. A reader that predated the change therefore decoded
the next field's bytes into the removed field, without any error, and
1.0 shipped a test asserting exactly that. 2.0 replaces the attribute
with two explicit forms:

| Attribute | Wire from version `N` | Readers that predate it | Notes |
|---|---|---|---|
| `retired = N` (new) | slot kept, holds the field's default | stay aligned, see the default | about 1 byte per value; safe with any reader rollout order |
| `removed = N` | slot gone | mis-decode the next field | exactly the 1.x `deprecated` bytes; reader-first rollout required |

Readers at version `N` or later discard a retired slot's contents, so a
writer can never leak a retired value into new readers. The spec text is
`docs/WIRE_FORMAT.md` §3.8 (spec 1.3). Tests cover old readers, new
readers and property-based round-trips in `tests/schema_evolution.rs`,
`tests/view_versioned.rs` and the `decode_view_derive` fuzz target.
`tests/golden_v2.rs` pins the bytes.

### Fixed

- **`DeserializeView` and versioned types** (PACK-006). Take

### Changed

- Map and set encoding uses one scratch buffer and skips the sort for
  already-ordered input.
- Versioned structs encode without a temporary buffer and decode without
  copying the body.

  allocation.
- Integer arrays read the canonical flag once per collection; scalar
  varints consult it only after a redundant zero byte.
- `pack-io-derive` uses syn 3, as serde_derive and rkyv do. It is
  pinned `=2.0.0`.
- The `schema` feature is documented as an alias for `derive`.
- CI:

## Canonical decoding stays opt-in

The README promises deterministic encoding, and it delivers it: a value
always encodes to the same bytes, and `HashMap` and `BTreeMap` with the
same entries encode identically. The question for 2.0 was whether
*decoding* should also refuse every other byte string by default. It
does not, for three reasons:

1. **Correctness.** Lenient decoding is correct: every valid encoding
   decodes to its value, and the spec permits lenient readers. What
   canonical mode adds is injectivity: exactly one accepted byte string
   per value. That only matters where the bytes themselves are trusted
   as an identity, such as hashes, signatures or deduplication keys.
2. **Streams.** Canonical mode needs the raw input, so a canonical
   default would make `IoDecoder::new` fail. Recording keys inside the
   streaming decoder was built and measured: it made *lenient*
   streaming decodes 30–60 % slower, so it was dropped.
3. **Cost.** On the in-memory decoder canonical mode costs about 23 %
   on small-key map decoding (4 % with string keys). That is far over
   the 5 % budget for every user who does not need it.

The escape hatch is per decoder or per call:
`Config::with_canonical(true)` with `decode_with_config`,
`decode_view_with_config`, `decode_from_with_config` or the serde
`from_slice_with_config`.

**What canonical mode guarantees.** For every type built from pack-io's
own impls and derives, a canonical decoder accepts exactly one byte
string per value: shortest varints, maps and sets in strictly increasing
encoded order, and versioned structs only at the reader's own version,
with no unread body bytes and retired slots holding the default. An
older frame is a second encoding of the defaulted value, and a newer one
carries fields the reader cannot check, so both are `NonCanonical`;
decode them leniently and re-encode if you need the canonical form. A
hand-written `Deserialize` impl or `with` helper is covered only if it
accepts one encoding per value itself, and serde set fields need
`sorted_set`.

## Performance

Measured with
[`benches/min_trials.rs`](https://github.com/jamesgober/pack-io/blob/main/benches/min_trials.rs)
and the same workloads against 1.0.1 (same harness, 1.0 API only). The
method takes the fastest of 300 trials × 2,000 iterations on a pinned
core, best of six alternating sessions per side. The machine is an AMD
Ryzen 9 9950X3D under WSL2 Ubuntu, rustc 1.99. Differences under about
6 % are noise on this shared machine.

| Workload | 1.0.1 | 2.0.0 | Change |
|---|---:|---:|---:|
| versioned struct encode | 37.8 ns | 14.8 ns | −61 % |
| versioned struct decode | 23.9 ns | 14.1 ns | −41 % |
| `BTreeMap<String, u64>` × 100 encode | 3.06 µs | 1.12 µs | −64 % |
| `BTreeMap<u32, u32>` × 100 encode | 4.07 µs | 3.31 µs | −19 % |
| `[u8; 32]` encode / decode | 14.5 / 15.3 ns | 5.3 / 0.8 ns | −64 % / −95 % |
| 64 KiB `Vec<u8>` decode | 884 ns | 554 ns | −37 % |
| log record decode (owned) | 76.2 ns | 62.1 ns | −19 % |
| log record encode / view | 25.3 / 25.8 ns | 24.2 / 26.6 ns | −4 % / +3 % |
| `BTreeMap<u32, u32>` × 100 decode | 901 ns | 893 ns | −1 % |
| `IoDecoder` `Vec<u64>` / map / 4 KiB `String` | 1.27 µs / 849 / 126 ns | 1.27 µs / 854 / 125 ns | within ±1 % |
| `u64`, 64-byte `String`, `&str` view round-trips | 5.8 / 17.1 / 13.0 ns | 6.2 / 16.7 / 13.3 ns | +6 % (noise) / −3 % / +3 % |
| **`IoDecoder` plain struct** | 15.5 ns | 18.8 ns | **+21 %** |

One row exceeds the 5 % budget and is recorded rather than hidden:
**`IoDecoder` plain struct** costs 3 ns more per struct. That is the
depth limit: every derived decoder enters and leaves one nesting level.
It is the price of rejecting stack-exhausting input on streams. On the
in-memory decoder the same work is within noise.

**`Vec<u64>` decode (re-audit PACK-R04).** The pre-release tree measured
`Vec<u64>` × 1000 decode at +12 % here and attributed it to code layout.
The re-audit showed the cause was the canonical-mode check on every
varint. Integer arrays now read the flag once per collection and run a
varint loop specialised for it. Re-measured with the re-audit's
min-of-trials harness (Windows 11, rustc 1.99, best of six alternating
sessions × 200 trials; 1.0.1, the pre-release tree, and this release):

| Build | Workload | 1.0.1 | pre-release | 2.0.0 |
|---|---|---:|---:|---:|
| default `release` | `Vec<u64>` × 1000 (multi-byte) | 1,545 ns | +10 % | **−16 %** |
| default `release` | `Vec<u64>` × 1000 (values < 100) | 927 ns | +21 % | **−19 %** |
| fat LTO | `Vec<u64>` × 1000 (multi-byte) | 1,603 ns | −0.4 % | **−37 %** |
| fat LTO | `Vec<u64>` × 1000 (values < 100) | 948 ns | −0.1 % | **−61 %** |

Map decode (`BTreeMap<u32, u32>` × 100) stays within ±5 % of 1.0.1 in
both builds. Loop placement moves single rows of this harness by up to
15 % between otherwise identical builds, so the LTO rows were confirmed
with loop alignment pinned (`-C llvm-args=-align-loops=64`): −37 % and
−63 %.

Against other codecs (same harness, 2.0.0), pack-io:

- is the fastest of pack-io, bincode, postcard and rkyv on the `u64`
  and 64-byte `String` round-trips, the `&str` view, and 4 KiB
  `Vec<u8>` decode;
- ties bincode on struct encode and rkyv on owned struct decode;
- loses to rkyv's archived access, which is about 2× faster than
  pack-io's zero-copy view. That loss is intentional.

The full table is in
[`docs/PERFORMANCE_BASELINE.md`](https://github.com/jamesgober/pack-io/blob/main/docs/PERFORMANCE_BASELINE.md).

## Known issues

- **Elements that occupy no input bytes** are bounded by `max_alloc`
  per decode, not by the input. Their charge is `size_of` the element;
  heap memory such an element owns itself (an `Rc` control block) is
  not counted, so `Vec<Rc<()>>` can peak at about three times
  `max_alloc`. Lower `max_alloc` for untrusted input that may contain
  such types.
- **Generic `[T; N]`** (element types other than the primitives) still
  decodes through a temporary `Vec` (PACK-R09): building the array in
  place needs `unsafe` or the unstable `core::array::try_from_fn`.
- **`IoEncoder` / `IoDecoder` do not buffer** (PACK-018). They issue one
  `write` / `read` call per primitive, so wrap raw sockets and files in
  `BufWriter` / `BufReader`, as the docs say. Internal buffering would
  make `IoDecoder` read past the value it returns, which would break
  `into_inner`.
- **`IoDecoder` rejects canonical mode.** Buffer the frame with
  `decode_from_with_config` (see above).

## What's next

- A buffered streaming decoder that hands back unread bytes, so
  `IoDecoder` can avoid one syscall per primitive without breaking
  `into_inner`.

## Stability promise

The post-1.0 contract carries forward:

- SemVer applies to the public API and to the wire format.
- Any breaking change gets explicit deprecation first, or a major
  version.
- The MSRV advances only on minor or major bumps; it stays 1.85.

2.x minor releases are additive. The wire format remains readable by
every later 2.x decoder.
