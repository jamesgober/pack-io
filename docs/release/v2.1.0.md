# pack-io v2.1.0: memory budget per message

**Released:** 2026-11-12
**Status:** stable minor release. The wire format is unchanged; every
2.0 encoding decodes to the same value. Decodes that build more memory
than the configured budget now fail with `SerialError::InvalidLength`.

---

## Summary

2.0 bounded every length-prefixed value by `max_alloc` and every
allocation by the input that backs it. An independent review in 2026-11
showed that this was not enough: some values are one byte on the wire
and kilobytes in memory, and `max_alloc` limited each value, not the
message. 2.1 charges what a decode actually builds in memory against one
budget per message, and adds a preset for peer input.

## What changed

### Security

- **In-memory size is charged, not wire size.** Every collection charges
  `size_of::<T>()` per element slot before its elements decode. `Box<T>`,
  `Rc<T>` and `Arc<T>` charge the value they hold. An element type that
  is much larger in memory than on the wire (an `Option` of a large
  array, an enum with a unit variant next to a large one) is bounded like
  everything else.
- **One total per message.** The slots above, every owned `String`,
  `Vec<u8>` and `Bytes`, and every boxed value draw on one running total,
  `Config::max_total_alloc`. It defaults to `max_alloc`, so the existing
  knob keeps working as a single limit. In-memory and streaming decoders,
  views and the serde adapter all charge the same way.
- **Element loops are bounded.** A collection element that consumes no
  input is charged at least 64 bytes, so a short input cannot keep a
  decoder looping for long.

### Added

| Item | Purpose |
|---|---|
| `Config::max_total_alloc` (field), `with_max_total_alloc(n)` | The budget for one decoded value; `None` means "same as `max_alloc`". |
| `Config::total_alloc_limit()` | The total in force. |
| `Config::network()`, `Config::NETWORK_MAX_ALLOC` | 16 MiB per value and per message: the starting point for peer input. |
| `Decode::reset_unbacked()` | Start a new budget. `Decoder::read`, `IoDecoder::read` and the serde entry points call it per top-level value. |

### Changed

- With a tight `max_alloc`, a message can now fail where 2.0 accepted
  it, because collection slots count: under `with_max_alloc(1 << 20)`, a
  `Vec<u64>` of 200,000 elements needs 1.6 MB of budget. Keep the small
  per-value cap and raise the message budget with
  `with_max_total_alloc`.
- With the default config, the change is visible only for a single
  message that builds more than 1 GiB.
- In-memory map and set encoding no longer copies every entry through a
  scratch buffer: entries are written in place and reordered only when
  they arrive out of order.

### Not changed

- `Config::DEFAULT_MAX_ALLOC` stays 1 GiB. Lowering it would break
  callers that decode large trusted values (snapshots, records) with the
  default config, so it is a candidate for the next major. Use
  `Config::network()` for peer input today.

## Upgrading from 2.0

Nothing is required for callers that decode with the default config.
Callers that set `max_alloc` low for peer input should check that their
largest legitimate message fits the same number as a total, or set
`with_max_total_alloc` explicitly. Code that decodes several values with
`T::deserialize` on one long-lived decoder (rather than `read`) should
call `Decode::reset_unbacked` between values.

`pack-io-derive` moves to 2.1.0 with no code change, to keep the two
crates in lockstep.

## Stability promise

Unchanged from 2.0: the 2.x public surface only grows, and the wire
format is frozen at spec version 1.3.
